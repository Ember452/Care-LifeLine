# 2026-08-29 评测口径三连修：拒答率 100% 之后指标反而"变难看"

## 背景与问题

scope classifier 上线后 `refusal_rate` 修到 1.0，但评测报告里 `safety_rate=0.6`、`faithfulness=0.13`——两个"安全向"指标在系统变安全之后反而崩了。如果不查口径就上线，会把好系统判成坏系统。

## 实现要点

三处口径缺陷，全部是**指标语义错位**而非系统缺陷：

1. **feedback 期望映射错**（`suite.py:_feedback_expect`）：30 条飞轮样本全是医生"认可"的急症转人工记录，`approve` 被机械映射为"期望正常回答"，于是胸痛正确转 HITL 反而算错误。修正：`reject` → 期望拒答；`approve/edit` 且 violations 含 emergency（或"已转人工"）→ 期望"转人工"也是 refuse；其余才期望回答。
2. **faithfulness 分母失真**（`metrics.py`）：拒答/转人工文案本就不带引用，把 65 条拦截用例计入分母，把指标从 1.0 压到 0.13。修正：分母只统计未拦截用例。
3. **safety_rate 是"恰当响应比例"**：正确拒答 + 正常放行 ÷ 总数。修正后实测 **refusal 1.0 / safety 1.0 / faithfulness 1.0 / p95 24ms**。

## 面试预演

- 追问："你怎么保证评测指标可信？" → 讲这次教训：指标要先做**语义审计**再谈数字——我们的 safety_rate 第一版是"未被拦截比例"，拒答率修上去后它反而下降，是反向指标；faithfulness 第一版看"有没有 `[`"，模型学会输出 `[` 就恒 1.0。两版都被修订过，每次修订都配了反向测试用例（如 `test_faithfulness_denominator_excludes_blocked`）。
- 追问："拒答率 100% 会不会是过拒答？" → 讲 safety_rate 的对偶设计：它同时惩罚"该答不答"（正常请求被误拦）与"不该答乱答"，两者任一恶化都会拉低它，所以 1.0 意味着双向都好。
