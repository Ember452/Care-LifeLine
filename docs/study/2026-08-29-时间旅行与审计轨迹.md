# 时间旅行、审计轨迹与"会越问越懂"的记忆

日期：2026-08-29 ｜ 关联：ADR-0017

## 背景与问题

三张支票一直没兑现：文档说"按 session 回放完整 trajectory"（工具轨迹
只进 SSE，重启即丢）、"checkpointer 时间旅行"（只有 HITL 在用
checkpointer）、"分诊上下文含用药/过敏/随访"（只有指标时序）。

## 实现要点

1. **trajectory 不建新表**：工具调用与质控结论作为审计事件经统一入口
   写入 `audit_logs`——"审计流即轨迹"。这是克制：审计入口是 AGENTS.md
   定下的架构约束，事件类型过滤已够查询粒度，新表是多余的物的分离。
2. **时间旅行的关键语义选择**：只做重放（fork），不做 update_state 写
   回——审计不可变性比"能改历史"重要。`ainvoke(None, config=
   {thread_id, checkpoint_id})` 即从该检查点续跑，LangGraph 会 fork
   追加新检查点、原历史只读。端点摘要只出 draft/qc 等关键字段，完整
   状态（含患者消息）不出接口。
3. **记忆注入的空值语义**：原 recall 节点"无指标即返回空"，导致只用
   用药史的 newNode 拿不到上下文；改为"指标与结构化摘要合并，全空才
   返回空增量"——不产出噪声记忆的原则保留，注入条件放宽。

## 面试预演

**Q：为什么轨迹放审计而不是单独的 traces 表？**
单一事实来源 vs 查询便利的取舍。审计入口是全项目约定的唯一写入口
（绕过即架构违规），事件类型 + detail JSON 已满足"按会话回放每跳"
的查询需求；真要结构化分析时，审计事件的 detail 是 JSON，ETL 到分析
表是下游的事。

**Q：时间旅行在生产有什么用？**
事故复盘：用户投诉某次回答，管理员从检查点历史定位当时的中间状态，
从任一检查点重放（mock/real 皆可）验证"换个模型/换个质控阈值会不会
不同结论"——这正是评测驱动开发的运行时形态。重放是 fork 不是改写，
历史可审计。

**Q：记忆为什么只存结构化字段？**
隐私边界（文档 §7.4）：自由文本可能夹带身份信息且难以脱敏审计；
结构化字段（药名/过敏原/计划）天然可枚举、可脱敏、可导出删除，
"越问越懂"的收益和 PHI 风险都被限定在可控范围。
