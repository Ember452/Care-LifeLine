# 审计轨迹闭环、时间旅行与纵向记忆结构化

## 背景

文档 §10.2 承诺"按 session_id 回放完整 trajectory"、§7.5 规划
checkpointer 时间旅行、§7.4 规划用药/过敏/随访结构化上下文——三项均未
落地。工具轨迹此前只进 SSE 与进程内指标，重启即失；纵向记忆只有指标
时序，分诊提示词拿不到"患者在用什么药、对什么过敏"这类安全关键信息。

## 决策

1. **轨迹经统一审计入口**：每跳工具调用（`tool_called`，detail 含
   tool/ok/latency/摘要）与质控结论（`qc_decision`）作为审计事件写入，
   不建新表、不绕过 `write_audit`——审计流本身就是 trajectory，
   `GET /v1/admin/audit/sessions/{thread_id}` 的语义随之升级。
2. **时间旅行端点**（admin 角色）：`GET .../checkpoints` 用
   `get_state_history()` 列检查点摘要（不含完整状态值，防 PHI 大对象
   出接口）；`POST .../replay` 传 `checkpoint_id` 后
   `ainvoke(None, config)` 从该点重放，同线程 fork 追加新检查点、原
   历史不变，重放动作写 `trajectory_replayed` 审计。无 checkpointer
   返回 409 而非 500。
3. **纵向记忆三张表**：`patient_medications` / `patient_allergies` /
   `patient_followups`（models 与 001_init.sql 同步）；
   `patient_memory` 增三组 append/list/状态流转函数与
   `structured_summary()`；`memory_recall_node` 把结构化摘要并入
   `memory_context`——仅有用药/过敏而无指标时也注入（原实现直接返回
   空）。隐私边界不变：只存结构化脱敏字段。
4. **明确不做**（各自理由）：语义缓存（文档明确"先不加"）、方案 C
   分块质控（演进预留）、Langfuse（自建采集点已按其埋点位置设计，
   接外部服务是加 exporter 的事）、MedQA/PubMedQA（英文数据集与中文
   产品口径不符，以自建检索 hit@k 评测替代）、CODEOWNERS 占位（需
   仓库所有者用户名）。

## 备选方案

- 工具轨迹单独建表：查询更结构化，但绕开了"审计统一入口"的既有架构
  约束（AGENTS.md 依赖方向节），且审计流已带事件类型过滤，够用。
- 时间旅行做"写回"（update_state 修改历史）：破坏审计不可变性语义，
  只做重放（fork 不改写）。

## 后果

- 管理端可对任一会话回答"每一步调了什么工具、质控怎么判、医生怎么
  改"，并可从任意检查点重演——配合 replay 端点可做事故复盘演示。
- 分诊提示词自动携带过敏史/在用药物，用药咨询的安全上下文闭环。
- 检查点摘要接口只出 draft 前缀级信息，PHI 出接口风险受控。
