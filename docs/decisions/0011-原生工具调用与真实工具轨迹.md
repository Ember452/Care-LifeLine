# 原生 tool-calling 与真实工具轨迹

## 背景

此前图中"多 Agent"实为「单 prompt 单节点 + 关键词路由」：全仓没有一次原生
tool-calling（`bind_tools` / ReAct 循环），工具调用是节点内硬编码直调；
SSE 的 `tool_call` 事件是 `chat.py` 用静态 `_TOOL_BY_NODE` 字典映射出来的
**展示性事件**，并非真实工具轨迹。更严重的是 medication 节点只产出
`medication_warnings` 而不产出 `draft`，QC 对空草稿判 refused——mock 模式下
用药咨询实际以通用拒答文案收尾。这与「多 Agent 平台」定位差距最大，也是
面试追问（"Agent 怎么自己决定调工具？失败怎么重试？"）必露馅的点。

## 决策

1. **Provider 协议扩展**：`LLMProvider` 新增 `invoke_with_tools(messages, tools,
   temperature, tier) -> AIMessage`（一轮原生 tool-calling）。工具以
   `ToolSpec`（name/description/parameters JSON Schema）描述；`CareTool`
   协议相应增加 `parameters` 类属性，注册表即 schema 的单一来源。
   - `RealProvider`：`ChatOpenAI.bind_tools(...).bind(temperature).invoke()`，
     OpenAI function calling 协议，返回可能携带 `tool_calls` 的 AIMessage。
   - `MockProvider`：确定性两轮脚本——首轮命中 `drug_interaction` 即发起
     工具调用，`ToolMessage` 回填后基于 JSON 结果生成最终回答。
2. **通用 ReAct 节点** `graph/nodes/tool_agent.py:run_tool_agent()`：
   模型自主决定是否/调用哪个工具，工具结果以 `ToolMessage` 回填继续推理，
   上限 `_MAX_TOOL_ROUNDS=3`；未注册工具与执行异常都转成 `ok=False` 轨迹
   + 错误结果消息回填，让模型改述而非整轮失败；轮数耗尽兜底拒答文案。
   中间消息只留在循环内部，不写回图状态（会话历史保持干净）。
3. **真实轨迹贯通 SSE**：state 新增 `tool_traces: list[ToolTrace]`
   （tool/args/ok/error/latency_ms/summary）；`chat.py` 从 updates 流读真实
   轨迹发 `tool_call` 事件，删除静态 `_TOOL_BY_NODE` 映射。
   `SSEToolCall` 契约（tool/args_preview/ok）不变，前端零改动。
4. **medication 节点改造成首个工具智能体**（async 节点，builder 用
   `functools.partial` 传入 provider 以保留 coroutine 语义）：ReAct 循环产
   `draft`，同时保留离线 DDI 确定性警示兜底模型漏检，双通道在 responder
   合并。修复"用药咨询被拒答"的缺陷。

## 备选方案

- 节点内继续硬编码调用工具、仅把事件流做真：放弃——模型仍无自主决策权，
  面试叙事不变。
- ReAct 循环用纯文本协议（自己解析 "Action:/Observation:"）：放弃，放弃
  结构化 `tool_calls` 的解析健壮性与 OpenAI 协议兼容性。
- QC（含 rewrite 回环）整体拆 subgraph：本轮不做。QC 子图需重构外部
  条件边与 SSE 节点命名，与 tool-calling 改造混在一个批次风险高，留作
  独立后续项。

## 后果

- mock 模式下工具循环同样走真通路（真实 trace、真实 ToolMessage 回填），
  eval 基线不变（refusal/safety 1.0，P95 24.1→26.3ms）。
- medication 意图从「空草稿 → QC refused → 通用拒答」变为「工具结果 →
  真实 draft → QC passed」，`SSEToolCall` 事件反映真实调用与失败。
- triage / report_interpreter / memory_recall 仍是单 prompt 节点（各自的
  职责不需要模型决策工具），后续按需逐个接入 `run_tool_agent`。
- real 模式行为依赖所选模型对 function calling 的支持（Doubao/DeepSeek
  OpenAI 兼容端点均支持）。
