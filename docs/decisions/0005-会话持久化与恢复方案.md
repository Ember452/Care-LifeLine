# 会话持久化与恢复不依赖 LangGraph Checkpointer

## 背景

M2-4 需要对话可跨请求恢复（多轮记忆、审计、反馈闭环）。原设计（`docs/superpowers/specs/...-design.md`）计划用 LangGraph 的 `PostgresSaver`/`SqliteSaver` 作为 checkpointer 挂接 `compile(checkpointer=...)` 实现状态恢复。

但在 TestClient（Starlette 的 anyio 阻塞 portal）下实测发现两个死锁：

1. **任意 LangGraph checkpointer（含 `MemorySaver`）配合 `graph.ainvoke` 都会让 TestClient 请求挂起**——LangGraph 在 checkpoint 读写时与 TestClient 的事件循环/portal 相互阻塞。
2. **`aiosqlite`（异步 SQLAlchemy）同样会在 TestClient portal 下死锁**；而一个不含 checkpointer、不触 DB 的最小端点（`graph.ainvoke` 直接返回）在 TestClient 下完全正常。

MVP 必须在无外部依赖（默认 SQLite）下可跑、可测，死锁不可接受。

## 决策

放弃用 LangGraph checkpointer 做跨请求恢复。改为：

- 持久化层使用**同步 SQLAlchemy 2.0（engine/sessionmaker）**，在异步端点内通过 `starlette.concurrency.run_in_threadpool` 调用，避免与事件循环争用。
- 会话恢复由我们自己的 `db/session_store` 负责：请求进入时按 `session_id` 载入历史消息（`get_prior_messages` → langchain `HumanMessage`/`AIMessage`），拼到初始 `state["messages"]`，再 `graph.ainvoke`。
- `graph.compile()` 不加 checkpointer（`builder.build_graph(provider=None)`）。
- PostgreSQL 仍通过 `CARE_DATABASE_URL=postgresql://...` 启用（`make_url` 自动转 `postgresql+psycopg`），`compose-up` 一键起；SQLite 为默认零依赖路径。

## 备选方案

- **保留 `PostgresSaver` + 异步 SQLAlchemy**：被否，因 TestClient 死锁无法在 CI/本地测试覆盖，且引入 async 复杂度对 MVP 收益低。
- **`graph.ainvoke` 改在独立线程跑（绕开 portal）**：可行但掩盖了"checkpointer 本身在 portal 下即死锁"的问题，且破坏流式响应语义，放弃。

## 后果

- 正面：默认 SQLite 零依赖可跑、58 个测试全绿、无异步死锁；恢复逻辑显式可控、易测。
- 负面：放弃 LangGraph 原生长程记忆/时间旅行能力，需自管 `messages` 拼接；未来若需 LangGraph 高级恢复，再评估在其官方"线程模式"下解决 portal 兼容性后再接回。
