# 评测双基线、LLM 裁判有据率与 QC 阈值校准

## 背景

改造前评测有两个"自嗨"问题：其一，`run_suite` 只跑 mock 栈且报告只有一份
（real 模式跑分会覆盖 mock 基线），"评测驱动"无从对证；其二，报告解读用例
在评测里硬编码 `MockReportInterpreter`——即使 real 模式跑，这一路仍是假
解释器。此外设计文档 §9.1 的语义级 faithfulness（ragas 式）与 §9.4 的
阈值校准（200 条标注 + PR 曲线选点）均未实现。

## 决策

1. **双基线分文件落盘**：mock → `eval_report.md`（CI 回归基线），
   real → `eval_report_real.md`；报告标题标注模式与裁判口径。`make eval` /
   `make eval-real` 各自对应，real 需 `CARE_LLM_MODE=real` + API Key。
2. **报告用例去 mock 残留**：`_run_report` 按模式选择解释器（real 用
   `LLMReportInterpreter`，与图内节点逻辑一致），并把用例的草稿摘要与
   引用一并交给裁判。
3. **新增有据率 groundedness（LLM-as-judge，§9.1 语义级 faithfulness）**：
   - 双实现与既有的 mock/real 分层同构：`MockGroundednessJudge`（确定性
     代理：真实引用存在性，CI 可回归）与 `LLMGroundednessJudge`（rubric
     逐断言核对，输出 `{"supported_ratio", "unsupported_claims"}` JSON）。
   - 只对**已回答且携带引用**的用例评测；被拦截/无引用不进分母。
   - 裁判解析失败返回 ``None``（该用例不计入），绝不把"裁判故障"记成
     0 分伪装成"回复无据"。
   - 不引入 ragas 依赖：ragas 拉取较重且 API 变动频繁、无法离线测试；
     自研裁判 prompt 与 `LLMReviewer` 同构（rubric + JSON + 降级解析），
     口径可解释、可单测。ragas 作为演进项保留。
4. **QC 阈值校准 harness（§9.4）**：`eval/calibrate.py` 对
   `data/eval/qc_calibration.json`（24 条 pass/block 标注草稿种子集，
   后续经 workbench 飞轮扩充）用 `LLMReviewer` 打分，扫描 0.05-0.95
   阈值输出 precision/recall/F1 表，F1 最优为推荐阈值；**并列时取召回
   更高者**——医疗场景漏放行的代价高于多转人工。仅 real 模式可跑
   （mock 评审员打分无语义意义，CLI 显式拒绝）。

## 备选方案

- real 基线写同一个 eval_report.md：放弃，双基线的价值就在于对照与回归。
- 直接引入 ragas：放弃（见上），接口保持与 ragas 对齐的
  `supported_ratio` 语义，后续可平滑替换。
- 校准在 mock 模式下跑：放弃，确定性打分对阈值校准是循环论证。

## 后果

- mock 基线新增 groundedness=1.0（引用存在性代理，与 faithfulness 同口径，
  符合预期）；real 模式跑完后两份报告可直接对比"裁判口径下的真实有据率"。
- 校准种子集 24 条偏小，推荐阈值置信度有限——这是显式声明的局限，
  扩充路径 = workbench 医生审核记录自动沉淀（数据飞轮既有机制）。
- 红线核查：qc_calibration.json 属评测标注数据，与 redteam/refusal 同目录、
  同样不进 RAG 语料与 prompt 模板。
